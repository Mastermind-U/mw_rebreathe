# Нулевой Master и аудиосессия игры

В v13 пользователь подтвердил затихание музыки, сначала сообщил об остающихся
шагах и воде при Master=0. Через 10–15 секунд вода затихла, но шаги оставались
слышны при Master=0, а затем и при Footsteps=0. Два traced CALL при этом
передавали нулевую громкость. Дополнительное чтение полного native списка
DirectSound device обнаружило 12 согласованных DSBF-буферов: у всех
сохранённая громкость, которую читает настоящий GetVolume, равнялась −10000.
Причина слышимого остатка этим снимком не установлена. Повторная установка
того же значения в трёх native SetVolume не доказана как исправление.

Следующий эксперимент добавляет отдельный mute аудиосессии **только процесса
Morrowind** при нулевом Master. Он выполняется в 64-битном host, а не в DLL
игры. Это настоящий флаг mute сессии; ненулевые уровни остаются штатными,
включая [исправление музыкального Master](music-volume.ru.md).
В игровом v14 пользователь подтвердил тишину при нулевом Master и возврат
звука после его повышения. Host зафиксировал одну подходящую сессию,
собственный SetMute(TRUE), успешный HRESULT и ноль ошибок. Наблюдение
завершения и финального Restore этого прогона сохраняется отдельно.

## Принадлежность и восстановление

Host перечисляет все активные render endpoints и их аудиосессии. Запись
допускается только при GetProcessId == S_OK и точном совпадении проверенного
PID, IsSystemSoundsSession == S_FALSE и известном состоянии сессии. Сессии
других процессов, системные звуки, cross-process результат и неоднозначные
ошибки отклоняются. Общий уровень устройства и уровни volume сессии не
меняются; изменяется только mute выбранной сессии, отражаемый и в Windows
Mixer. Область ISimpleAudioVolume ограничена shared-mode
аудиосессией; exclusive-mode потоки этим интерфейсом не управляются.
[Microsoft ISimpleAudioVolume](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nn-audioclient-isimpleaudiovolume),
[Microsoft GetProcessId](https://learn.microsoft.com/en-us/windows/win32/api/audiopolicy/nf-audiopolicy-iaudiosessioncontrol2-getprocessid).

Перед первым собственным SetMute(TRUE) сохраняется прежнее состояние mute.
Уже заглушённая сессия не становится собственностью мода и никогда им не
разглушается. При ненулевом или неизвестном Master выполняется восстановление
только собственных изменений. Восстановление использует снимок состояния
перед первым собственным mute. Повторный poll не переписывает уже установленный
mute. Если guard продолжает действовать, внешний unmute будет снова заглушён
при следующем poll. Отдельные изменения mute через Windows во время действия
guard не отслеживаются: восстановление использует первоначальный снимок.

Mute сессии может сохраняться между её экземплярами, поэтому expiration или
ошибка устройства не считаются успешным восстановлением. Сохраняются прежнее
состояние и обязательство восстановления. При переподключении допускается
перенос этого обязательства на новый instance только для той же пары
endpoint ID / SessionIdentifier и того же точного PID. Различающий экземпляры
SessionInstanceIdentifier используется отдельно. Сам по себе прежний PID
не разрешает воздействие на новый процесс.
[Microsoft Audio Sessions](https://learn.microsoft.com/en-us/windows/win32/coreaudio/audio-sessions),
[Microsoft GetSessionInstanceIdentifier](https://learn.microsoft.com/en-us/windows/win32/api/audiopolicy/nf-audiopolicy-iaudiosessioncontrol2-getsessioninstanceidentifier).

Host держит проверенный HANDLE процесса от привязки до завершения Restore и
деструктора guard; одна host-сессия обслуживает одну игру. Даже после выхода
игры передаётся последний проверенный PID этого удерживаемого процесса.
Это позволяет повторить восстановление, не перепривязываясь по одному лишь
повторно использованному числу PID.

Ошибка Restore сохраняет ownership для следующего вызова. Если устройство
остаётся недоступным до закрытия host, восстановление не гарантируется:
финальные ownedMutes/errors выводятся в журнал. Нет бесконечных повторов,
ожидания переподключения, записи в registry или управления будущими PID.
При принудительном завершении host деструктор не вызывается и сохранённый
mute приложения может остаться. Этот preview не содержит watchdog или
журнал восстановления для такого завершения.

## API и поток

AudioSessionMuteGuard::Update(exactPid, masterKnown, masterZero), Restore,
Stats и деструктор вызываются на одном host-потоке. Он же создаёт, использует
и освобождает COM-интерфейсы. Инициализация использует MTA; несовместимая
COM apartment отклоняется до записей. Чужой поток отклоняется. Update и
Restore сохраняют LastError, не выпускают исключений и не создают worker
threads, timer callbacks или DllMain/atexit hooks. Период poll задаёт host.
Mute применяется после обнаружения соответствующей сессии, поэтому это не
гарантия отсутствия звука до первого успешного poll.

Stats сообщает lastResult, matchedSessions, ownedMutes, changes, errors и
initialized. Перед уничтожением guard host явно вызывает Update с неизвестным
Master и удерживаемым PID, затем Restore, записывает финальную статистику и
только после COM cleanup освобождает HANDLE процесса. Деструктор выполняет
ещё одну конечную попытку Restore без циклов ожидания.

## Проверки

Из каталога audio:

~~~cmd
session-mute-test-build.cmd
session-mute-test-build.cmd --observe-only 23056
~~~

Скрипт собирает x64 utility и fixture с /W4 /WX. Обычный запуск выполняет
110 проверок на fake backend без изменения настоящего звука: точный PID,
cross-process и system reject, две конечные точки, прежний mute, пять
нормальных путей восстановления, COM/get/set/enumeration failures, S_FALSE,
исключения, повторные попытки, expired restore, invalidated reconnect с
унаследованным mute, немедленный Master>0 после reconnect, отсутствие чужих
PID writes, неизвестный PID, единственный поток и LastError.

Observe-only utility не содержит SetMute/SetMasterVolume. Она только
перечисляет сессии и читает состояние подходящего PID. В живой v13 для
PID 23056 найдена одна активная сессия на одном render endpoint:
GetProcessId=S_OK, IsSystemSoundsSession=S_FALSE, mute=FALSE, volume=1.0.
Всего перечислено семь сессий; одна cross-process сессия отклонена.
Никакие параметры аудио этим наблюдением не изменялись. Это подтверждает
доступность подходящей сессии, но не проверяет звучание после нового mute.
